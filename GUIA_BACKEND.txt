1. VISÃO GERAL EM 1 MINUTO
--------------------------------------------------------------------------------
- O front (Next.js, apps/web) fala com a API por JSON em /api/*.
- A API é ASP.NET Core "Minimal APIs": cada rota é uma linha `MapGet/MapPost`.
- Dados em PostgreSQL (produção) ou SQLite (dev, zero instalação), via EF Core
  (você escreve C#/LINQ, ele gera o SQL).
- Regras de negócio ficam em "Services"; tudo que fala com o mundo externo
  (pagamento, CEP, imagens, e-mail) fica atrás de uma interface com uma
  implementação fake para dev e uma real (Mercado Pago, ViaCEP, R2, SMTP).

Rodar: pnpm api (http://localhost:5210, docs em /scalar) · Testar: pnpm api:test
Contas de dev: demo@mktpy.com/123456 (comprador + dono da MegaStore) e
admin@mktpy.com/admin123 (administrador, definido em Admin:Email/Password).

2. AS QUATRO CAMADAS  (apps/api/Marketplace.slnx)
--------------------------------------------------------------------------------
  Marketplace.Api            rotas HTTP, JWT, CORS, JSON, tratamento de erros
      ↓ usa
  Marketplace.Infrastructure EF Core, seed, Mercado Pago, ViaCEP, R2, jobs
      ↓ usa
  Marketplace.Application    regras de negócio (Services), DTOs, interfaces
      ↓ usa
  Marketplace.Domain         entidades, enums, Money, máquina de estados

Regra: uma camada só conhece a de baixo. Domain não depende de nada (testável
sem banco); Application define INTERFACES (IPaymentGateway...) e Infrastructure
as implementa — trocar de gateway não mexe no checkout; Api é só "cola".

Onde está o quê:
  Domain/Common          Money (inteiro), Documents (CPF/RUC/CEP), DeterministicId
  Domain/Entities        classes que viram tabelas · Domain/Enums.cs
  Domain/OrderStateMachine.cs · Domain/ImportTaxCalculator.cs
  Application/Abstractions  interfaces · Application/Contracts  DTOs (= JSON)
  Application/Services   Catalog, Seller, Shipping, Checkout, Order, Payment,
                         Payout, Auth, Account, Privacy, SellerPanel, Admin
  Infrastructure/Persistence  AppDbContext, Migrations, Seed
  Infrastructure/{Payments,Shipping,Storage,Auth,Email,Background}
  Api/Program.cs (inicialização) · Api/Endpoints/*.cs (rotas)

3. O CAMINHO DE UMA REQUISIÇÃO  (GET /api/products/smart-tv-55-ele1)
--------------------------------------------------------------------------------
 1. Middlewares (Program.cs): erro → CORS → rate limit → autenticação (lê o
    JWT) → autorização → output cache.
 2. Rota em CatalogEndpoints.cs:
      g.MapGet("/products/{slug}", (string slug, CatalogService svc,
                                    CancellationToken ct) => svc.ProductAsync(slug, ct));
    `slug` vem da URL; `svc` vem do container de injeção (DI); `ct` avisa se o
    cliente desconectou. Em POST, um parâmetro complexo (`LoginRequest body`) é
    lido do corpo JSON.
 3. O Service consulta com LINQ:
      await db.Products.AsNoTracking().Include(p => p.Seller)
        .FirstOrDefaultAsync(p => p.Slug == slug, ct) ?? throw AppException.NotFound("Produto");
 4. O mapper (Common/Mappers.cs) converte entidade → DTO; o DTO vira JSON
    camelCase, enums como texto, datas UTC com "Z" (Api/Infrastructure/JsonSetup.cs).

 Erros: `throw AppException.Validation("cpf", "CPF inválido.")` → 422 com
 { status, code, message, errors: { cpf: [...] } }; NotFound → 404; Conflict →
 409; Unauthorized → 401; qualquer outra exceção → 500 sem vazar detalhes.
 O front lê `errors` e mostra a mensagem no campo certo.

4. BANCO DE DADOS
--------------------------------------------------------------------------------
EF Core: cada classe em Domain/Entities é uma tabela; `AppDbContext` tem um
`DbSet<T>` por tabela e `OnModelCreating` com o mapeamento fino. Consulta com
LINQ, grava com `db.Add(x)` + `await db.SaveChangesAsync(ct)`.

Tabelas (snake_case automático): categories, sellers, seller_categories,
products, product_images, product_variants, reviews, questions, banners,
coupons, users, refresh_tokens, password_reset_tokens, addresses, favorites,
cart_items, consents, audit_logs, exchange_rates, shipping_zones,
checkout_quotes, purchases, orders, order_items, order_events, tracking_events,
payments, payouts, webhook_events, platform_settings.

Relações: users 1─N addresses/refresh_tokens/consents · sellers 1─N products ·
products 1─N images/variants/reviews/questions · purchases 1─N orders, 1─1
payments · orders 1─N order_items/order_events/tracking_events.

Detalhes que surpreendem (AppDbContext.cs):
- Enums gravados como TEXTO ("Pago"): `HasConversion<string>()`.
- Listas/dicionários e snapshots viram JSON em coluna de texto (portável).
- `User.Cpf` e `Payment.PayerDocument` são CIFRADOS (Data Protection). Nunca
  filtre por CPF no SQL.
- Datas sempre DateTime UTC (conversor força Kind=Utc).
- `Roles` é lista gravada como "Comprador,Vendedor" — filtro por papel é feito
  em memória (AdminService.ListUsersAsync).
- Índices únicos: slug, e-mail, RUC, número do pedido, (userId, idempotencyKey),
  (provider, externalId) dos webhooks.
- Projeções em consultas usam CLASSES com inicializadores (`new Row { A = .. }`),
  não records posicionais: o EF só traduz Where/OrderBy sobre membros quando a
  projeção é por inicializador (ver as "Row" no AdminService).

SQLite x PostgreSQL: sem `ConnectionStrings:Postgres` → SQLite em
apps/api/src/Marketplace.Api/.data/marketplace.dev.db com `EnsureCreated()`;
com Postgres → `Migrate()` aplica Persistence/Migrations. Mudou entidade? Gere
migration (seção 15); em dev basta apagar o .db.

Seed: SeedCatalog porta as fixtures do front com os MESMOS GUIDs
(DeterministicId = mulberry32 + FNV-1a do mock). SeedDemo (só com
Database:SeedDemoData=true): usuário demo, 2 endereços, 11 pedidos, dono da
MegaStore. SeedAdminAsync cria o admin de Admin:Email/Password.

5. DINHEIRO, CÂMBIO E IMPOSTOS
--------------------------------------------------------------------------------
Money (Domain/Common/Money.cs): `readonly record struct Money(long Amount,
CurrencyCode Currency)`. Amount é INTEIRO na menor unidade (R$ 1.299,00 =
129900; PYG sem centavos). Percentuais em basis points (10000 = 100%).
`RoundDiv` arredonda half-up igual ao Math.round do JS — o backend bate
centavo a centavo com o mock do front.

Câmbio: fração exata numerator/denominator (BRL→PYG = 1389/100). A taxa é
TRAVADA no checkout (id na cotação, no pedido e no pagamento). O admin publica
novas cotações em /admin/exchange-rates; pedidos antigos mantêm a taxa.

Imposto (ImportTaxCalculator): modo Flat (alíquota única, padrão 60%) ou
RemessaConforme (20% até US$ 50; 60% − US$ 20 acima; ICMS 17% por dentro).
Sempre ESTIMATIVA. Parâmetros em platform_settings (editáveis em
/admin/configuracoes).

6. PEDIDO: MÁQUINA DE ESTADOS
--------------------------------------------------------------------------------
  AguardandoPagamento → Pago → EmPreparacao → Enviado
      → EmTransitoInternacional → Entregue → Concluido
  Ramos: Cancelado (até EmPreparacao) · EmDisputa (a partir de Enviado)
         → Devolvido → Reembolsado, ou → Concluido

`OrderStateMachine.CanTransition(de, para)` é a fonte de verdade.
`OrderService.Transition(order, status, note, location, actor)` valida (409 se
proibido), muda o status e grava uma linha em order_events (timeline). A
descrição do evento é gerada na leitura pelo idioma (Common/Messages.cs); só
`Note` (texto extra, ex.: "Admin: ...") vai ao banco.

Quem transita: gateway/webhook (→Pago), vendedor (→EmPreparacao→Enviado),
transportadora (→EmTransito→Entregue), comprador (Cancelado, EmDisputa,
Concluido), admin (qualquer transição válida + resolver disputa), job
(Entregue→Concluido após AutoCompleteDays).

--------------------------------------------------------------------------------
7. CHECKOUT E PAGAMENTO
--------------------------------------------------------------------------------
POST /checkout/quotes: valida CEP, carrega produtos por loja (pertencimento,
variação, estoque), cota frete, aplica cupom (inválido = ignora), calcula
imposto e total, grava a cotação (JSON, 15 min) e devolve `quoteId`.

POST /orders: idempotente por `idempotencyKey`; cotação expirada/consumida ou
frete diferente do cotado → 422. Em TRANSAÇÃO cria Purchase, 1 Order por loja
(PY-AAAA-NNNNNN), itens, timeline, Payment Pendente e DECREMENTA estoque
(desconto/imposto rateados para a soma bater com a cotação). Fora da transação
chama o gateway: Pix (payload + 30 min), boleto (linha digitável/PDF/3 dias),
cartão (aprovado → Pago; recusado → cancela e devolve estoque). Se o gateway
explodir, marca Recusado e cancela — sem pedido fantasma.

Depois: POST /webhooks/payments (assinatura HMAC, idempotente por id) aplica
Aprovado/Recusado/Expirado/Estornado; PaymentMaintenanceJob expira Pix/boleto
(e no fake aprova após 20 s). Cancelar pedido pago → estorno parcial;
todos cancelados → pagamento Estornado. Ao aprovar, PayoutService cria 1
repasse por pedido: bruto − comissão − custo do meio de pagamento, agendado
para paidAt + PayoutHoldDays (o imposto fica com a plataforma).

8. AUTENTICAÇÃO, PAPÉIS E BLOQUEIO
--------------------------------------------------------------------------------
- Login/registro devolvem accessToken (JWT HS256 com sub/email/name/roles) +
  refreshToken (aleatório; só o SHA-256 vai ao banco). O front manda
  `Authorization: Bearer ...`; `.RequireAuthorization()` bloqueia sem token.
- `ICurrentUser` lê o usuário do token em qualquer Service (`RequireUserId()`).
- Refresh rotativo com detecção de reuso (revoga tudo). Access token de 7 dias
  até o front ter o interceptor 401→refresh.
- Papéis (UserRole): Comprador, Vendedor, Admin. Virar vendedor REEMITE a
  sessão (o JWT antigo não tinha o papel). Rotas /admin/* exigem
  `RequireRole("Admin")`; o resto é 403.
- Bloqueio (User.BlockedAt, pelo admin): login e refresh recusam com 403
  ACCOUNT_BLOCKED; conta, checkout e painel do vendedor também checam
  (`AuthService.EnsureNotBlocked`). Bloquear revoga os refresh tokens.
- Senha com PasswordHasher (PBKDF2); login errado → 422 genérico no campo
  `password`. Google via idToken (Auth:Google:ClientId).

9. PAINEL DO VENDEDOR  (SellerPanelService, /seller/*)
--------------------------------------------------------------------------------
- Loja ligada ao usuário por `Seller.OwnerUserId`. `RequireSellerAsync`: sem
  loja → 403 SELLER_REQUIRED (front redireciona ao cadastro); suspensa → 403.
- POST /seller/register valida (RUC módulo 11 único, categorias, termos), cria
  a loja aprovada, adiciona o papel Vendedor e devolve loja + nova sessão.
- Produtos: validação campo a campo, slug único, SearchText para busca, imagens
  reordenadas (1ª = capa); DELETE = arquiva. Só `Ativo` de loja `Aprovado` vai à
  vitrine.
- Pedidos: /seller/orders, prepare (Pago→EmPreparacao), ship (código de
  rastreio → Enviado + evento POSTED).
- Imagens: POST /seller/uploads assina URL; PUT direto; provider Local serve em
  GET /api/media/{key} (URLs relativas para passar pelo proxy do Next).

10. PAINEL DO ADMIN  (AdminService, /admin/*, papel Admin)
--------------------------------------------------------------------------------
Acesso: link alternativo /admin/entrar (mesmo /auth/login; o front só deixa
passar quem tem o papel Admin). O único admin é criado pelo seed a partir de
Admin:Email / Admin:Password (variáveis Admin__Email / Admin__Password em
produção). Para promover outro usuário: PUT /admin/users/{id} com roles.

Cada área é "entrável e crudável": lista com busca/filtro/paginação →
detalhe → edição/ação. Toda ação grava em audit_logs.

  GET  /admin/overview        totais (usuários, vendedores, produtos, pedidos),
                              produtos a caminho, aguardando envio, disputas,
                              vendas 30 d e total, imposto estimado, comissão,
                              repasses pendentes, pedidos por status,
                              histórico de vendas por dia (30 pontos), recentes
  Usuários    GET /users (q, role, blocked) · GET/PUT /users/{id} ·
              POST block/unblock · DELETE (anonimiza, LGPD)
  Vendedores  GET /sellers (q, status) · GET/PUT /sellers/{id}
              (status Aprovado/Pendente/Suspenso, reputação 1–5, loja oficial)
              Suspender tira TODOS os produtos da vitrine (CatalogService filtra).
  Produtos    GET /products (q, status, sellerId) · PUT (status, preço, estoque, nome)
  Pedidos     GET /orders (status, q, sellerId, userId, inTransit=true) ·
              GET /orders/{id|número} (pedido + comprador + pagamento + repasse) ·
              POST /orders/{id}/transition { status, note, trackingCode } —
              respeita a máquina de estados; cancelar devolve estoque ·
              POST /orders/{id}/disputes/resolve { outcome: Devolvido |
              Reembolsado | Concluido } — Reembolsado estorna no gateway
  Pagamentos  GET /payments (status, q) · POST /payments/{id}/refund (total)
  Repasses    GET /payouts (status, sellerId) · POST mark-paid | processing | retry
  Cupons      GET/POST /coupons · PUT/DELETE /coupons/{id}
  Câmbio      GET/POST /exchange-rates (nova cotação publicada com validade)
  Banners     GET/POST/PUT/DELETE /banners · Categorias POST/PUT /categories
  Config      GET/PUT /settings (modo/alíquota de imposto, ICMS, comissão,
              custo do meio de pagamento, frete grátis, prazos, versões dos termos)
  Auditoria   GET /audit (q)

Proteções: o admin não bloqueia, não exclui nem remove o próprio papel Admin
(409); repasse já pago não volta; só pagamento Aprovado pode ser estornado.

--------------------------------------------------------------------------------
11. JOBS EM BACKGROUND  (Infrastructure/Background/Jobs.cs)
--------------------------------------------------------------------------------
`BackgroundService` roda um loop enquanto a API está de pé; cada volta abre um
scope novo (DbContext não é thread-safe). PaymentMaintenanceJob (5 s): expira
pagamentos, auto-aprova no fake. LogisticsJob (15 min): consulta rastreio,
aplica eventos (dedupe por ExternalId), transita, conclui entregues antigos.

12. LGPD E SEGURANÇA
--------------------------------------------------------------------------------
consents versionados (cadastro e cadastro de loja) · GET /me/data-export ·
DELETE /me e DELETE /admin/users/{id} anonimizam (nome, e-mail, CPF, telefone,

DataProtection:KeysPath — PERDER = perder os CPFs; faça backup) · rate limit
em /auth/* e exportação · nomes públicos abreviados · cartão só por token ·
erros nunca vazam stack trace fora de Development.

13. CONFIGURAÇÃO  (appsettings.json + appsettings.Development.json)
--------------------------------------------------------------------------------
Qualquer chave vira variável de ambiente trocando ":" por "__"
(Auth:Jwt:Secret → Auth__Jwt__Secret). Segredos: `dotnet user-secrets`.
  ConnectionStrings:Postgres   vazio = SQLite
  Database:SeedDemoData        true só em dev
  Admin:Email / Admin:Password administrador único (dev: admin@mktpy.com/admin123)
  Auth:Jwt:Secret              ≥ 32 chars, OBRIGATÓRIO · AccessTokenMinutes
  Payments:Provider            Fake | MercadoPago (+ AccessToken, WebhookSecret, NotificationUrl)
  PostalCodes:AllowOfflineFallback  true em dev
  Tracking:Provider            None | Fake (+ WebhookSecret)
  Storage:Provider             Local | R2 (+ R2:*) · LocalPublicBase "/api"
  Email:Provider               Log | Smtp
  Links:SiteUrl / ApiUrl       URLs públicas · Cors:Origins · DataProtection:KeysPath
As opções chegam ao código por `services.Configure<X>(config.GetSection(..))`
e `IOptions<X> options` no construtor → `options.Value`.

14. SINTAXES DE C# QUE APARECEM O TEMPO TODO
--------------------------------------------------------------------------------
Primary constructor:  class CatalogService(IAppDbContext db, TimeProvider clock)
  os parâmetros viram campos; quem os passa é o container de DI.
record:  record LoginRequest(string? Email, string? Password) — classe imutável
  com igualdade por valor; `with { }` copia alterando campos; `record struct`
  é a versão tipo-valor (Money).
Nulos:  string? = pode ser null · a ?? b · a?.Prop · x! ("confie") ·
  `required` = obrigatório na criação · `if (x is { } v)` = "não é null, guarde em v".
async/await/ct:  toda chamada a banco/rede é `async Task<T> ...Async(.., ct)`.
LINQ:  db.Orders.Where(o => o.UserId == id).OrderByDescending(o => o.CreatedAt)
  .Skip(20).Take(10).ToListAsync(ct) — em DbSet vira SQL; Include = JOIN;
  Any = EXISTS; Select projeta; GroupBy agrupa.
Pattern matching:  status is A or B · x switch { "a" => 1, _ => 0 } ·
  input.Price is null or < 100.
Coleções:  List<string> x = [] · [.. lista, novo] · string[] a = ["a"].
DI (DependencyInjection.cs):  AddScoped (1 por requisição: DbContext, Services)
  · AddSingleton (1 para sempre: JWT, storage) · AddHostedService (jobs).
  Singleton NÃO recebe Scoped no construtor (jobs abrem scope na mão).
Minimal APIs:  g.MapGet("/{id}", (string id, Svc svc, CancellationToken ct) =>
  svc.GetAsync(id, ct)); devolver o DTO = 200; Results.Created/NoContent/File.
  GET e DELETE não inferem corpo: use [FromBody].
Exceções de negócio:  AppException.Validation/NotFound/Conflict ·
  ValidationErrors acumula campos e `ThrowIfAny()` lança um 422 só.
EF gravar:  db.X.Add(e) INSERT · alterar entidade rastreada UPDATE ·
  db.X.Remove(e) DELETE · SaveChangesAsync executa tudo em transação ·
  AsNoTracking() = só leitura. Transação explícita: BeginTransactionAsync/Commit.
TimeProvider:  `clock.GetUtcNow().UtcDateTime` no lugar de DateTime.UtcNow.

15. RECEITAS
--------------------------------------------------------------------------------
A) Endpoint novo: DTO em Application/Contracts (+ espelho TS em
   packages/contracts) → método no Service (ou Service novo registrado com
   AddScoped) → rota em Api/Endpoints → teste em tests/.
B) Coluna/tabela: propriedade na entidade (ou classe + DbSet em IAppDbContext e
   AppDbContext) → mapeamento se preciso → migration:
     cd apps/api
     dotnet ef migrations add Nome --project src/Marketplace.Infrastructure --startup-project src/Marketplace.Api --output-dir Persistence/Migrations
   (dev SQLite: apague o .db) → DTO + mapper se aparece no JSON.
C) Trocar gateway: implemente IPaymentGateway e registre em
   Infrastructure/DependencyInjection.cs conforme Payments:Provider.
D) Ligar Mercado Pago: Payments__Provider=MercadoPago + AccessToken +
   WebhookSecret + NotificationUrl (URL pública + /api/webhooks/payments); no
   front, tokenizar o cartão com o SDK JS e enviar card.token + brand.
E) Mudar taxas/impostos/prazos: painel admin → Configurações (platform_settings).
F) Criar outro admin: /admin/compradores → usuário → papéis → marcar Admin.
G) Resetar o banco de dev: pare a API, apague .data/marketplace.dev.db, suba.

16. DEPURAÇÃO E GLOSSÁRIO
--------------------------------------------------------------------------------
Logs no console (rota, status, tempo; 500 com stack) · /scalar para testar
rotas (logue, copie o accessToken) · SQL gerado: subir o log de
Microsoft.EntityFrameworkCore.Database.Command para Information · SQLite: "DB
Browser for SQLite" · `pnpm api:test` sobe a API em memória com SQLite.
Erros comuns: "Body was inferred..." → [FromBody] em GET/DELETE · "Kind=Local"
no Npgsql → data não UTC · "The LINQ expression ... could not be translated"
→ projeção com record posicional ou lógica não traduzível: projete com classe
+ inicializador ou traga para memória (ToList) antes · 405 em rota existente
→ conflito de método no roteamento.

DTO objeto só de dados (o JSON) · Entidade linha de tabela · DbContext sessão
com o banco · Migration alteração de schema · Scoped/Singleton tempo de vida
no DI · Middleware etapa do pipeline HTTP · JWT token assinado com o usuário ·
Refresh token só para obter JWT novo · Idempotência repetir não duplica ·
Webhook o gateway chama a API · Basis points 1/100 de 1% · Snapshot cópia
congelada (endereço/frete no pedido) · Slug id legível na URL · Seed dados
iniciais · HMAC assinatura do webhook · Anonimizar apagar o que identifica
mantendo o histórico fiscal.
